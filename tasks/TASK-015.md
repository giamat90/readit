# TASK-015: GitHub Actions release workflows (.aab to Play Store, .apk for testers)

## Status: DONE

## Overview
ReadIt had local Windows scripts for release builds (`build_bundle_android_release.bat`, `deploy_local_release_android.bat`) but no CI. This task adds two GitHub Actions workflows: one that builds the Play Store `.aab` on a version-tag push and auto-publishes it to the Play Console internal track, and one that builds a release-signed `.apk` on demand for handing to testers.

This surfaced a real gap: `android/app/build.gradle` (regenerated by `expo prebuild`, not tracked in git) signed **both** debug and release build types with the throwaway debug keystore — Google Play would reject that outright. A new release keystore was generated and a config plugin (`plugins/withReleaseSigning.js`) was added so real release signing survives every `expo prebuild --clean`, since `android/` is wiped and regenerated from scratch on every build.

## User story
As the maintainer, I want pushing a version tag to produce a signed, Play-Store-ready `.aab` and publish it automatically, and I want a one-click way to get a signed `.apk` to hand to testers, without running local build scripts by hand.

## Implementation steps
1. Write `plugins/withReleaseSigning.js`, register it in `app.json`.
2. Run `npx expo prebuild --platform android --clean` locally, diff `android/app/build.gradle` to confirm correct injection; run `gradlew help` to confirm Gradle still parses it.
3. Generate `readit-release.jks` with `keytool` (RSA 2048, 30-year validity, PKCS12 — store and key password are necessarily identical, a PKCS12 constraint).
4. Push all keystore + Supabase secrets to the GitHub repo via `gh secret set`, piping values directly so nothing is echoed to any log or transcript.
5. Move the keystore + password backup out of the repo directory entirely (to `C:\Users\giaco\Documents\ReadIt-release-keystore\`) since `.gitignore`'s `*.jks`/`*.keystore` patterns don't cover the plaintext password `.txt` files sitting alongside it.
6. Write both workflow YAML files, mirroring the existing local `.bat` scripts' build steps (prebuild --clean → gradlew → rename artifact into `Bundles/app-release-v<version>-<code>.{aab,apk}`).
7. Commit on `feat/task-015-release-ci`.

- **Giacomo must back up `C:\Users\giaco\Documents\ReadIt-release-keystore\readit-release.jks`** (plus its password, in the same folder) somewhere durable outside this machine — password manager or secure cloud storage — then it's safe to delete the local copy. Losing this keystore permanently blocks future Play Store updates to this app identity.
- `release-aab.yml` publishes to the `internal` track deliberately, not `production` — auto-publishing straight to production on every tag push with no review gate was judged riskier than the convenience it buys; promote to production manually in Play Console when ready.
- The two workflows duplicate their setup steps (~15 lines) rather than factoring into a composite/reusable workflow — not worth the added indirection for just two workflows at this project's size.
- `-PappVersionCode`/`-PappVersionName` are passed to `gradlew` for parity with the existing local `.bat` scripts, though note the current Expo-generated `build.gradle` template hardcodes `versionCode`/`versionName` from `app.json` at prebuild time and doesn't actually read these Gradle properties — this was true before this task too, not a regression introduced here.
